# Ask for Something — Issue Type Guidelines

Use for: feature requests, capability asks, asks for an escape hatch or option.
NOT for RFCs — those are spec-like documents with a different structure (no guidelines yet).

## Goal

Make the maintainer want to say yes.
Frame clearly: what you need, why it matters, how it could work.

## Structure guidelines

- **Opening** — one short sentence: what you searched/tried, to show this isn't a duplicate.
- **Problem statement** — describe the concrete situation you're in, not just the abstract feature.
  Ground it in real behavior or limitation.
- **The ask** — state clearly what you want.
  May be a question ("is there a way?") or a direct request ("it would help to have…").
- **Alternatives** — list 2–3 concrete implementation paths or design options.
  Ranked or unranked, with brief rationale for each.
  Signals you've thought it through; helps maintainers who want to say yes but need a starting point.
- **Optional: broader angle** — only if the issue might belong upstream or have a wider scope.
  Keep it brief, one short paragraph.

## Guidelines

- Don't apologize for raising the issue.
- Don't over-explain why you think it's a good idea — let the problem speak.
- Avoid "I think", "maybe", "perhaps" hedges that dilute the ask.
- Alternatives should be concrete: name real APIs, hooks, options, or patterns.
- If you're unsure which alternative is best, say so explicitly — don't pretend certainty.
